# DocAgent

An autonomous AI agent that converts a plain-English request into a fully formatted Word document — planning its own steps, retrieving relevant structure via RAG, generating grounded content, and producing supporting data visualizations, all through a single API call.

**Live demo:** https://docagent-kk5e.onrender.com
**API docs:** https://docagent-kk5e.onrender.com/docs

> Note: hosted on Render's free tier — the first request after a period of inactivity may take 50+ seconds due to cold start. This is a hosting characteristic, not a bug in the pipeline itself.

## What It Does

Give it a request like *"Create a project plan for a website redesign"* and it will:

1. **Plan autonomously** — classify the request into a document type and generate its own step-by-step plan, stating any assumptions made if the request is ambiguous
2. **Retrieve context (RAG)** — match the request against a local knowledge base of document templates to ground generation in a consistent structure
3. **Generate content** — write real, detailed content for each planned section, grounded in the retrieved template
4. **Build visualizations** — generate a budget breakdown pie chart and a project timeline chart
5. **Assemble the document** — compile all sections and charts into a polished, downloadable `.docx` file

### Supported document types

- Project Plan
- Meeting Minutes
- Business Proposal
- SOP (Standard Operating Procedure)
- Technical Design Document

The category list is fixed, but which category applies to a given request — and how to fulfill it — is decided by the agent at runtime, not hardcoded.

## Architecture

```
Request → Planner (autonomous planning + assumption handling)
        → Retriever (TF-IDF + cosine similarity over document templates)
        → Shared Context Generator (one consistent set of facts for the whole doc)
        → Generator (section-by-section content generation, RAG-grounded)
        → Chart Generator (budget + timeline visualizations)
        → Doc Builder (final .docx assembly)
        → Response (file + reasoning)
```

**Stack:** FastAPI · Groq (Llama 3.3 70B) · scikit-learn (TF-IDF) · python-docx · matplotlib

Roughly 8–10 LLM calls per document: 1 for planning, 1 for shared context, 4–6 for section content (depending on plan length), and 2 for chart data.

## Key Engineering Decisions

- **TF-IDF instead of neural embeddings for retrieval.** `sentence-transformers` was the first choice for true semantic matching, but the `torch` install kept timing out on a slow connection. TF-IDF + cosine similarity via scikit-learn is lexical rather than semantic, but for a small, fixed set of five templates it's sufficient — a deliberate simplicity-vs-extensibility tradeoff that wouldn't scale as-is to hundreds of more varied templates.
- **One LLM call per section instead of one call for the whole document.** Trades speed for more focused, higher-quality content per section.
- **A shared-context generation step runs once, before section generation.** All sections draw from the same set of generated facts (names, dates, budget), preventing the sections from contradicting each other.

## Bugs Found & Fixed

**Retrieval matching the wrong template.** A request for meeting notes was scoring higher against the SOP template than the meeting-minutes template, because of a coincidental shared word ("notes") combined with no stopword filtering over a very small corpus. Fixed by filtering common stopwords and injecting each template's own name into its text for a stronger identity signal — turned a narrow, incorrect match into a clear, correct one.

**Cross-section content inconsistency.** Since each section was generated by an independent LLM call, sections would invent contradictory mock details across the same document (e.g. a name or role changing between sections). Fixed by adding a `generate_shared_context()` step that runs once up front, so every section prompt reuses the same set of facts instead of inventing its own.

## Known Limitations

- Retrieval always returns the best-scoring template with no minimum-similarity threshold or fallback — even a poor best match still gets used
- Chart data is generated via a separate LLM call from the document text, so in rare cases numbers could diverge slightly between the chart and the written content
- Retrieval index rebuilds on every request rather than being cached in memory — fine at small scale, not optimized for high request volume
- No persistence layer — templates are local files; generated documents aren't stored beyond the request/response cycle
- Tested for correctness on the assignment's required cases plus a handful of informal ones; no formal load testing or measured success/failure rate at scale

## Running Locally

```bash
git clone https://github.com/satyamrathod6669/DocAgent.git
cd DocAgent
pip install -r requirements.txt
```

Set your Groq API key as an environment variable, then run the FastAPI app:

```bash
uvicorn main:app --reload
```
